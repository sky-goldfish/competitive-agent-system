核心数据流：一次完整分析的全生命周期

Step 1 用户输入需求 → POST /api/runs → start_run() 写入 DB → 后台启动 execute_discovery_run()
Step 2 Graph 1 执行：需求理解(LLM) → 竞品发现(Search+LLM) → 人工确认 → DB 写入 Competitors → status=waiting_for_human
Step 3 用户选择竞品 → POST /api/runs/{id}/competitors/confirm → 后台启动 execute_report_run()
Step 4 Graph 2 执行：资料采集(Search) → 结构化分析(LLM) → 报告生成(LLM) → 质量检查(LLM) ⇄ 条件循环（最多3轮）
Step 5 每阶段完成通过 on_stage_complete 回调持久化 Sources / Evidence / Analyses / Report / QAResult → status=completed

Retrieval Quart 资料采集模式

material_collection_node 的核心：为每个竞品×每个缺失的 schema 槽位生成一个"检索规划书"，发给搜索 API，对返回结果打分取最优。

用一个例子走一遍

假设正在分析竞品 Notion，发现它的"价格与商业模式"维度还缺资料。

Step 1：选模板 → 生成 query
已知：竞品名=Notion、slot=pricing、locale=global、product_type=software

_quart_query() 查 SaaS 英文模板：
"{product} pricing plans enterprise"
→ 填入 product=Notion
→ query = "Notion pricing plans enterprise"
Step 2：同时生成评分偏好
_preferred_source_types(software, direct, pricing)
→ ["official_pricing_page"]

这是写死在代码里的：定价维度的最可信来源就是官方价格页。

另外硬编码基础权重表：
官方价格页 0.93、评测 0.82、社区 0.62…
Step 3：发搜索 → 分类 → 打分
把 "Notion pricing plans enterprise" 发给搜索 API，拿回 4 条结果。

搜索查询体系总览

系统在竞品发现和资料采集两个阶段共生成 3 类搜索场景、50+ 条查询模板变体，按产品类型(SaaS/实物商品)、语言区域(中文/英文)、竞品关系类型和 Schema 槽位自动选择。

阶段一：竞品发现
目标理解 query + 竞品搜索 query + 官网解析 query
共 ~9 条查询，中英文混合
阶段二：资料采集 (Retrieval Quart)
7个schema槽位 × 2产品类型 × 2语言区域 × 4竞品类型 × N个竞品
共 48+ 条查询模板变体
QA 补充搜索
质检发现信息缺口后，LLM 动态生成针对性补充 query
格式：{competitor_name, slot, query}

Query 生成变量说明

变量来源说明
{product}competitor.name竞品名称
{name}competitor.name同上
{target_name}target_understanding.name 或 requirement.target_product分析目标/用户自己的产品
{competed_need}_infer_competed_need() 推断竞品与目标争夺的用户需求（如"团队协作"、"保温需求"）
{overlap_text}overlap_points 前2项拼接竞品与目标的重叠维度描述
{domain}requirement.domain 或 possible_market_category市场领域
{category}target_understanding.category产品分类
{description}requirement.product_description 或 summary产品简短描述

搜索策略：limit & 并行度

阶段每 query limit并发线程数备注
目标理解搜索4min(4, query数)快速获取目标基本信息
竞品发现搜索5min(4, query数)更多结果以提高竞品发现覆盖率
官网解析5min(4, 候选竞品数)按竞品并行
资料采集 (Retrieval Quart)4min(4, query数)每个 Quart 独立搜索，结果经分类评分后取 top-2

搜索结果通过 _serialize_result() 统一序列化为 {title, url, snippet, provider, source_type} 格式，后续来源分类和可信度评分的计算独立于搜索provider。
